### 1.3 当前技术分层与术语边界

> 这部分用于统一后续讨论，避免把 agent、skill、MCP、RAG、记忆、OpenClaw 混成一层。

| 层 | 概念 | 当前角色 | 当前项目里的对应物 |
|---|---|---|---|
| L0 | **确定性能力** | 不依赖 LLM 的基础能力层 | `scheduler.py` `mastery.py` `phases.py` `notify.py` 等 |
| L1 | **Tool / Skill** | 可被上层调用的标准能力接口 | `core/tools.py` 统一工具注册表 |
| L2 | **Workflow** | 固定编排的多步流程 | 讲解自检工作流、路径生成流程、推荐流程 |
| L3 | **Dynamic Workflow** | 运行时按规则或状态选路的流程 | `recommend.py` `replan.py` |
| L4 | **Agent** | 具备长期身份、上下文和主动推进能力的角色层 | LearnBuddy 教练、未来个人助理模式 |
| L5 | **外部 Agent Runtime** | 承载高阶自治代理的外部运行时 | OpenClaw / 未来托管 agent runtime |

#### Tool / Skill / MCP / Agent 的关系

| 概念 | 作用 | 在 LearnBuddy 中的定位 |
|---|---|---|
| **Tool** | 可调用的单个能力接口 | 是最基础的可组合单元，如 `get_graph`、`recommend_today`、`check_replan` |
| **Skill** | 一组能力 + 提示词 + 使用约束的打包方式 | 未来接 OpenClaw 或其他 agent runtime 时的能力包形态 |
| **MCP** | 把 tools 暴露给外部 agent 的标准协议层 | `mcp_server.py` 已是对外桥接层 |
| **Agent** | 使用 tools / skill 持续完成目标的角色 | LearnBuddy 个人助理模式与 OpenClaw 接入层 |

#### RAG / Memory / OpenClaw 的边界

| 概念 | 解决什么问题 | 当前定位 |
|---|---|---|
| **RAG** | 让内容生成基于资料与来源，降低幻觉 | 内容可信度与知识检索层 |
| **Memory** | 让系统长期“记住这个用户是谁、怎么学、哪里容易卡住” | 个性化与长期陪伴层 |
| **OpenClaw** | 提供高阶自治代理运行时与跨端主动执行能力 | 升级模式承载层，不是主系统真相源 |

#### 当前技术判断

- 主系统仍然是 **LearnBuddy Web/PWA + core 引擎**
- `tools / MCP / memory / scheduler / notify` 是后续所有 agent 化扩展的公共地基
- `OpenClaw` 不是替代 LearnBuddy，而是未来个人助理模式的外部 runtime 或接入层

## 2. 数据模型

### 2.1 现有（V0）

`Message` / `DomainCategory` / `Intensity` / `InstanceStatus` / `EvalQuestion` / `EvalResponse` / `BaselineSummary` / `Milestone` / `WeeklyTheme` / `LearningMethods` / `UserParams` / `DaySlot` / `WeekDay` / `WeekPlan` / `Instance`。

### 2.2 V0.5 新增模型

```text
UserProfile          # 结构化用户画像
  ├─ dimensions: list[ProfileDimension]   # N 个能力维度
  └─ ProfileDimension
       ├─ name: str               # 维度名（领域适配，如"语法基础"）
       ├─ independent_score: 0-5  # 独立完成评分
       ├─ with_ai_score: 0-5      # AI 协作评分
       └─ evidence: str           # 评分依据

EvalScoring          # 单题判分结果
  ├─ question_id / independent_score / with_ai_score / comment

DailyQuiz            # 每日小测（5-10 题）
WeeklyExam           # 每周章考（30 分钟）
MonthlyExam          # 月度大考（5+1 测）
WeeklySelfCheck      # 6 关自检结果 + R1 判断

DaySlot 扩展字段：
  + resources: list[str]    # 具体资源（书/视频/题集 + 页码/集数）
  + quantities: str         # 量化（如"背 20 词 / 做 5 题"）
  + acceptance: str         # 验收标准（如"能默写 18/20"）

UserMemory           # 个人记忆（跨任务/跨会话，区别于单任务 UserProfile）
  └─ items: list[MemoryItem]
       ├─ layer: M1画像 | M2偏好 | M3错题弱项 | M4行为 | M5背景
       ├─ content: str           # 一句话记忆（如"偏好先看例子再看规则"）
       ├─ source: str            # 来源（eval / lesson / chat / checkin）
       ├─ instance_id: str|None  # 来自哪个学习任务（跨任务时为 None）
       ├─ confidence: 0-1        # 置信度（多次印证升高）
       ├─ updated_at: datetime
       └─ active: bool           # 巩固时淘汰→false（软删，可被用户编辑）
```

## 3. LLM 调用规范 ⚠️ 关键

> 修复 E-缺口2（async 阻塞）与 E-缺口3（无超时）。

### 3.1 同步 / 异步边界（强制）

| 场景 | 调用方式 | 原因 |
|---|---|---|
| CLI / 测试 / 脚本 | `client.chat(...)` 同步 | 无事件循环，直接阻塞 OK |
| FastAPI 流式对话 | `async for ... client.chat_stream(...)` | 原生异步，逐 token yield |
| **FastAPI 内的同步 LLM 调用** | `await asyncio.to_thread(fn)` | **禁止**在 async handler 里直接调同步 `client.chat`，会阻塞整个 event loop |

**当前 bug**：`server.py` 的 SSE handler 里 `generate_instance(params)` 是同步的，且内部 `build_learning_manual` 再调一次同步 `client.chat`，阻塞整个循环 ~5s。

**修复**：
```python
inst_dir = await asyncio.to_thread(generate_instance, params)
```

### 3.2 超时与降级

| 层级 | 超时 | 降级 |
|---|---|---|
| 连接级 | 60s（现有）| 抛 `LLMNetworkError` |
| **首 token** | 15s（V0.5 新增）| 提示用户"模型响应慢，请重试" |
| 评估出题 | 已有 fallback 题集 | 退化到通用题 |
| 学习手册 | 已有 fallback 模板 | 退化到模板 |
| 周计划生成（V0.5）| LLM 失败 | 退化到 V0 写死模板 |

> 原则：**任何 LLM 输出都要有"看得到的回退路径"**，不能静默失败。

## 4. 评估闭环设计（V0.5）

> 修复 P-缺口4：把 `evaluator.py` 从死代码接进运行路径。

### 4.1 当前问题

`system.md` 让 LLM 在对话中"口头"出题，`evaluator.py` 的 `BaselineEvaluator` 从不被调用 → 评估结果无结构化、无判分、不回流画像。

### 4.2 目标闭环

```text
对话挖掘目标
   ↓
evaluator.generate_questions(domain, hint)  → EvalQuestion[]
   ↓
前端 answer.html 双坐标系答题  → EvalResponse[]
   ↓
scorer.score(questions, responses)  → EvalScoring[]   (LLM 判分)
   ↓
profiler.build(scorings)  → UserProfile   (结构化画像)
   ↓
generator 消费 UserProfile → 弱项加权的对靶路径
```

### 4.3 两种接入方式（待决，见 PRD Q2）

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 对话内出题（LLM 口头）| 体验连贯，无跳页 | 难结构化、难判分 |
| B. 独立答题页 `answer.html` | 可结构化、可双坐标、可判分 | 多一次跳转 |

**倾向**：B 方案（独立答题页），因为它是把画像/考核做扎实的前提。

## 7. 运维约束 ⚠️ 关键

> 修复 E-缺口1：iCloud venv 导致启动卡死。

### 7.1 venv 不进 iCloud（强制）

**根因**：项目位于 `~/Library/Mobile Documents/com~apple~CloudDocs/...`，Python `import` 时每个文件 `read()` 被 iCloud daemon 拦截按需下载，启动卡几分钟（实测进程栈停在 `_io_FileIO_readall_impl → read()`）。

**约束**：
- venv 必须建在**本地非同步路径**，如 `~/.local/share/itutor/.venv`。
- 运行时可写数据（`data/instances/`、日志）建议同样移出 iCloud 或用本地软链。
- iCloud 只同步**源码**（用 git 做真正的版本同步）。

### 7.2 启动脚本约束

- `scripts/start.sh` 需检测 venv 是否在 iCloud 路径，若是则告警并引导重建到本地。
- 前台启动优先（`python -m uvicorn`），避免 sandbox 后台进程被 nice 节流。

### 7.3 进程与并发

- V0/V0.5 单 worker 够用；务必遵守 §3.1 不阻塞事件循环。
- 会话池 `_sessions` 需加 TTL + 上限（修复 B3 内存泄漏）。

## 9. 多端联通架构（手机端 ←→ web）

> 对应 [01 需求方案 §6 多端策略](./01-需求方案.md)。核心原则：**一个后端、一份数据、多个触点**。提醒做成 **web 应用自身能力（PWA + Web Push）**，与公众号解耦；不便用 Web Push 的用邮件兜底。手机端只"提醒 + 跳回 web"，不重做学习。

### 9.1 联通拓扑

```text
web / PWA 前端 ──┐
                 ├──→ FastAPI（/api/*，共享会话/实例/画像/记忆）──→ data/
                 │            │
                 │            ├─ 推送调度器（APScheduler 每日 cron）
                 │            ├─ Web Push（VAPID / pywebpush）→ 系统通知栏
                 │            └─ Email sender（SMTP）→ 每日 digest 兜底
```

> 推送抽象成**多通道**：调度器算出"今日推送负载"后，按用户偏好下发（`webpush` 优先，`email` 兜底）。新增通道只加一个 sender，不动调度逻辑。公众号**不在提醒链路里**（仅作内容/拉新，见 PRD §6.4）。

### 9.2 新增接口（V1，V0.5 先预埋空实现 + 字段）

| 端点 | 作用 | 阶段 |
|---|---|---|
| `GET /api/instance/{id}/today` | 拉取"今日任务"负载（今日 slot + 到期 micro-review）| V0.5 预埋 |
| `GET /api/review/today` | 拉取所有到期复习项（跨实例聚合）| V0.5 预埋 |
| `POST /api/review/submit` | 回写闪卡/小测结果，更新间隔重复状态 | V0.5 预埋 |
| `POST /api/push/subscribe` | 保存 Web Push 订阅（endpoint + keys），即"开启提醒"| V1 |
| `POST /api/notify/prefs` | 设置提醒时间 / 通道（webpush / email）/ 开关 | V1 |
| `POST /api/push/test` | 调试用：手动触发一条提醒 | V1 |

### 9.3 推送链路（Web Push 优先，邮件兜底）

```text
APScheduler 每日 08:00（按用户通知偏好时间）
   ↓
为每个 active 实例算"今日推送负载"= 今日任务 + 到期 ReviewItem + 自检提醒
   ↓
按用户偏好通道分发：
   ├─ webpush（默认）：pywebpush 按 PushSubscription 下发 → service worker → 系统通知栏
   └─ email（兜底/未授权 Web Push）：SMTP 发每日 digest
   ↓
用户点通知/邮件里的深链 → 打开 web/PWA /today → 完成后 POST /api/review/submit 回写
```

> iOS 说明：Web Push 需 iOS 16.4+ 且页面"添加到主屏"后才可用；未满足的用户自动落到 email 通道。

### 9.4 数据模型预埋（V0.5 就加，避免 V1 改 schema）

```text
ReviewItem            # 间隔重复项（反遗忘 5 机制的载体）
  ├─ instance_id / item_text / source_lesson
  ├─ due_date: date          # 下次到期复习日
  ├─ interval_days: int      # 当前间隔
  ├─ ease: float             # 难度系数（SM-2 简化）
  └─ last_result: str        # again/hard/good/easy

PushSubscription      # Web Push 订阅（用户在 web 点"开启提醒"后保存）
  ├─ user_id / endpoint / p256dh / auth
  └─ created_at

NotificationPref      # 提醒偏好
  ├─ daily_time: "08:00"          # 每日提醒时间
  ├─ channel: webpush | email     # 主通道，未授权 Web Push 自动 email
  ├─ email: str | None
  └─ enabled: bool
```

### 9.5 PWA 落地要点（V1）

- `web/manifest.json`：name / icons / `display: standalone`，支持"添加到主屏"。
- `web/sw.js` service worker：监听 `push` / `notificationclick` + 缓存今日任务（离线可用）。
- 复用现有 web 技术栈（原生 HTML+JS），只是加"开启提醒"开关 + 窄屏自适应，**不重写**。
- VAPID 密钥与 SMTP 配置走 `.env`（`VAPID_PUBLIC/PRIVATE_KEY`、`SMTP_*`），不入代码。

### 9.6 分期落地

| 阶段 | 交付 |
|---|---|
| **V0.5** | 预埋 `ReviewItem` schema + `/today` `/review/*` 接口（可先返回今日 slot）|
| **V1** | PWA（manifest + sw）+ Web Push（VAPID/pywebpush）+ 邮件兜底 + APScheduler 调度器 + 用户体系 |
| **V1.5** | 视 Web Push 国内到达数据，评估补**小程序 + 订阅消息**做更好的原生通知 |

## 10. 账号、支付与权益技术前置

> 这部分用于支撑“手机验证码登录 + 支付 + 积分 + 个人助理模式收费”的后续落地。

### 10.1 手机验证码登录前置

| 项 | 技术要求 |
|---|---|
| 短信服务商 | 提供模板、签名、发送回执与成本控制 |
| 验证码存储 | 不存明文，需 hash + 过期时间 |
| 风控 | 限频、IP/设备维度限流、异常号码拦截 |
| 账号绑定 | 明确老用户绑定手机号与重复手机号冲突处理 |
| 审计 | 保留发送、验证、失败记录 |

### 10.2 支付前置

| 项 | 技术要求 |
|---|---|
| 支付通道 | 先确定微信支付、支付宝或聚合支付 |
| 订单系统 | 唯一订单号、订单状态机、幂等处理 |
| 回调处理 | 验签、重复通知去重、失败补偿 |
| 权益发放 | 支付成功后积分/订阅幂等发放 |
| 退款回滚 | 退款后积分回收或补偿逻辑清晰 |
| 对账与风控 | 至少支持基础对账、异常订单检测 |

### 10.3 当前技术建议

- 先把 **手机号登录、支付、积分、权益** 做成独立但可关联的基础模块
- LearnBuddy 主系统仍然是用户、学习记录、权益和积分的真相源
- 个人助理模式只是消费这些权益，不单独维护一套账

### 10.4 账号、支付与权益技术架构图

```text
用户
  ↓
Auth API
  ├─ password login
  └─ phone code login
        ↓
  PhoneVerification

用户账户 User
  ↓
Order / PaymentRecord
  ↓
Entitlement
  ├─ subscription
  └─ points grant
        ↓
PointsAccount / PointsLedger
        ↓
LearnBuddy 主系统消费
  ├─ 路径生成
  ├─ 学练 / 推荐 / 复习
  └─ 个人助理升级模式
```

### 10.5 支付链路时序

```text
前端提交购买请求
  ↓
创建 Order（pending）
  ↓
拉起支付渠道
  ↓
渠道异步回调
  ↓
验签 + 幂等检查
  ↓
更新 Order / PaymentRecord
  ↓
发放 Entitlement
  ↓
写入 PointsLedger / 更新 PointsAccount
  ↓
前端查询到新权益并生效
```

### 10.6 技术边界

| 边界 | 当前要求 |
|---|---|
| 账户真相源 | 用户账户、订单、积分、订阅统一在 LearnBuddy 主系统维护 |
| 支付位置 | 支付只发生在主系统 API，不在 OpenClaw / 飞书 / 微信侧自行建账 |
| 幂等 | 订单创建、回调验签、权益发放、退款补偿都必须幂等 |
| 风控 | 手机验证码限频、IP/设备维度控制、异常订单检测不可后补 |
| 外部运行时 | OpenClaw 只能读取/消费权益，不能绕过主系统直接改账 |

## 11. 个人记忆系统架构（越用越懂你）

> 对应 [01 需求方案 §7](./01-需求方案.md#7-个人记忆系统越用越懂你)。`core/memory.py` 是承载 D6 的核心模块。设计要点：**结构化优先、写入即抽取、读取即召回、定期巩固防膨胀**。

### 10.1 三条路径

```text
① 写入（write）  事件触发：eval / lesson / chat / checkin 结束后
     V0.5：规则写入（评估→M1画像、答错→M3弱项、打卡→M4行为）
     V1  ：LLM 抽取「记忆增量」（从会话/学练里提炼 M2偏好/M5背景）
     → upsert 到 UserMemory（同义合并、confidence 累加）

② 巩固（consolidate）  定期/达阈值触发
     合并重复、淘汰过期/低置信（active=false）、控制条目上限
     → 防 prompt 膨胀与 token 成本失控

③ 读取（recall）  生成路径 / 每日推荐 / 教练对话 前
     按当前领域+任务召回 Top-K 相关记忆
     V0.5/V1：结构化筛选（按 layer + instance + confidence 排序）
     V2  ：向量语义召回
     → 拼成「关于这位学习者」段注入 prompt
```

### 10.2 关键接口（`core/memory.py`）

| 函数 | 作用 | 阶段 |
|---|---|---|
| `write(events) -> None` | 事件 → 记忆增量 upsert | V0.5 规则版 / V1 LLM 版 |
| `recall(domain, instance_id, k) -> list[MemoryItem]` | 召回相关记忆 | V0.5 |
| `render_for_prompt(items) -> str` | 记忆 → "关于这位学习者"提示段 | V0.5 |
| `consolidate(user) -> None` | 合并去重、淘汰、限额 | V1 |

### 10.3 注入点（谁消费记忆）

| 消费方 | 注入内容 | 效果 |
|---|---|---|
| `generator` 路径生成 | M1/M3/M5：弱项 + 背景 | 下一次路径更对靶、举例贴背景 |
| `content` 内容生成 | M2/M3：偏好 + 弱项 | 按你喜欢的方式讲、优先练弱项 |
| `engine` 教练对话 | M2/M4：偏好 + 行为 | 语气与节奏适配，及时干预掉线 |
| 每日推荐（V1）| M3/M4：到期弱项 + 行为 | 今日任务对靶、防流失 |

### 10.4 工程约束

- **成本**：召回 Top-K（默认 K≤8）+ 巩固限额，避免 prompt 无限增长。
- **降级**：记忆为空或召回失败 → 退化为无记忆生成（不阻断主流程）。
- **隐私/透明**：记忆按 user 隔离，提供查看/编辑/删除接口（V1 记忆面板）；软删 `active=false` 保留可追溯。
- **持久化**：V0.5 随用户存 JSON（`data/users/{uid}/memory.json`），V1 入 DB，V2 向量库。

### 10.5 分期

| 阶段 | 交付 |
|---|---|
| **V0.5** | `UserMemory` schema + `core/memory.py` 规则版 write/recall/render + 评估/学练写入 |
| **V1** | LLM 记忆抽取 + consolidate + 召回注入生成/教练 prompt + 记忆面板 API |
| **V2** | 向量记忆（语义召回）+ 长期巩固"记忆雪球" |
