LearnBuddy × AI-Shifu：个性化 AI 学习产品对比分析报告

基于 AI-Shifu v2.2.4 release、README、ARCHITECTURE 与本地代码克隆分析，判断两者的定位差异、技术可借鉴点，以及 LearnBuddy 下一阶段应优先补强的课程运行时、深度搜索与内容质量闭环。

01

核心定位判断

两个产品都在做 AI 学习，但不是同一种起点。AI-Shifu 更偏“专家内容 AI 化”，LearnBuddy 更偏“个人目标自动变成学习系统”。
LearnBuddy 学习伙伴

用户目标驱动的个人学习系统

用户用自然语言说想学什么，系统负责澄清目标、即时诊断、深度搜索、生成路径、安排每日任务，并根据学习过程持续调整。

  • 起点是学习者本人，而不是创作者先准备课程。
  • 核心资产是用户画像、基线评估、学习路径、每日学习记录与学情闭环。
  • 适合不限领域的长周期个性化学习：语言、编程、写作、职业转型等。
  • 当前短板是教学内容生成深度、课程运行时结构、概念理解与来源链路。
AI-Shifu

创作者/机构的 AI 私教课程交付平台

创作者或培训团队提供专业知识、教学意图和课程框架，AI-Shifu 将其扩展成可个性化交付的学习体验。

  • 起点是专家内容与教学意图，面向创作者、教师和企业培训团队。
  • 核心资产是课程脚本、互动问答、发布流程、课堂/听课模式和运营后台。
  • 技术上更重视课程 authoring、publish、runtime、provider adapter 和观测。
  • 不宜被 LearnBuddy 全量照抄，否则会过早进入创作者平台复杂度。
02

一句话结论

AI-Shifu 值得学“课程运行与交付工程”，LearnBuddy 应坚持“个人学习路径与动态诊断”。

LearnBuddy 下一步不应该优先做课程商城或创作者运营，而应该先把内容生成从“prompt 写一篇课文”升级为“深度搜索 + 教学设计 + 互动运行时 + 质量评审 + 数据回流”的完整工作流。

03

从用户路径看，AI-Shifu 在“课程生产/交付”上更完整，LearnBuddy 在“个人诊断/计划/陪学”上有更强差异点。

04

架构对比

AI-Shifu 的代码结构对我们有启发：内容不是一次性文本，而是被拆成 service、provider、runtime、frontend renderer、trace 的多层系统。
AI-Shifu

Backend

Flask 服务，业务按 service 模块拆分：learn、shifu、billing、dashboard、profile、tts、metering 等。

Learning Runtime

learn 目录包含 ask provider adapter、context、state machine、lesson feedback、listen/player 等运行时逻辑。

Frontend

Next.js 前端，ChatUi、ContentBlock、InteractionBlock、ListenMode、CourseCatalog 等组件化较充分。

Observability

架构文档明确 request-id、Langfuse tracing、logs/traces/metrics 的最小验证闭环。

↔
LearnBuddy

Backend

FastAPI + SQLite，多用户、积分、RAG、推荐、重规划、阶段闸门、SM-2 调度已具备。

Learning Runtime

当前 lesson/cards 已有雏形，但还没有统一 LessonFlow、元素状态机、局部重生成和来源质量链路。

Frontend

原生 HTML 快速迭代，适合 V0，但学习页和计划页需要被结构化数据驱动，而不是继续靠页面拼接。

Observability

已有 trace/usage 基础，但还缺内容质量评审、生成链路追踪、用户痛点每日分析的系统视图。

05

代码级观察

以下来自本地克隆目录的直接观察，不只是 README 层面的产品介绍。
Provider Adapter

多后端接入方式清晰

AI-Shifu 在 `ask_provider_adapters` 里抽象 LLM、Dify、Coze、Coze Workflow、Volc Knowledge。LearnBuddy 也应抽象 LLM、搜索、RAG、视频源和评估器。

State Machine

流式内容有明确状态

`type_state_machine.py` 用状态机处理 element、break、audio、done、error。我们也需要对学习卡片、用户回答、反馈、下一步进行显式状态管理。

MarkdownFlow

内容是可运行结构

AI-Shifu 的学习内容围绕 block、element、interaction、feedback 持久化。LearnBuddy 应建立 `LessonFlow`，支撑回看、重生成、分析和复盘。

08

建议落地路线

下一轮最重要的不是继续改 UI 文案，而是让内容生产、内容运行和数据回流变成可控系统。
Phase 1 · 1-2 周

LessonFlow 课程运行时

  • 定义 lesson / step / element / interaction schema
  • 支持已学环节回看与局部重生成
  • 把来源、用户输入、反馈、完成状态落库
Phase 2 · 2-3 周

深度搜索与素材包

  • 创建 source_pack：官方文档、论文、文章、视频、案例
  • 概念不清时先搜索再澄清
  • 没有来源的正式内容降低可信等级
Phase 3 · 3-5 周

多角色内容工作流

  • Research / Planner / Lesson Designer / Critic 分层
  • 教学指标：深度、互动性、产出、迁移、复习
  • 自动修复浅内容、错概念、缺来源问题
Phase 4 · 5 周后

分析后台与创作者雏形

  • 内容质量 dashboard
  • 用户痛点每日自动分析
  • 内部课程版本、预览、发布，再考虑外部创作者
09

不建议照搬的部分

AI-Shifu 是成熟方向参考，但 LearnBuddy 现在不能被它的复杂度带偏。
暂不照搬

完整创作者平台

课程商城、创作者分销、复杂发布运营先不要做。LearnBuddy 当前核心是个人学习质量，而不是内容市场。

暂不迁移

前端技术栈重构

当前原生 HTML 仍适合快速验证。需要先稳定 LessonFlow 数据结构，再决定是否迁移 Next.js。

谨慎扩张

过多 provider

先把接口抽象做好，优先接通 DeepSeek、Bocha、本地 RAG 和质量评审，其他平台后续按需求接。

10

下一步建议：三件最值得做的事

这三件事会直接改善你最近反馈最多的问题：内容浅、概念误解、学习页不像真正的学习体验。
顺序任务为什么先做验收标准
1LessonFlow + 元素状态机没有运行时结构，前端再怎么改也只是展示一段内容。每个环节可回看、可重做、可局部重生成，学习记录按 element 保存。
2深度搜索 source_pack解决 harness 这类概念误判，以及“本节暂无外部来源”的可信问题。每个正式学习主题至少有 3-8 条来源，来源分官方/论文/文章/视频/案例。
3内容 Critic 质量闸门防止模型生成浅内容、泛泛而谈、练习不贴合目标。内容生成前后有评分：深度、准确性、互动性、来源完整度、可执行性。
1

LessonFlow + 元素状态机：把“内容”变成可运行的学习体验

解决“学习页像一段说明文”“学过不能回看”“只能单向往后”“重生成不知道改哪里”的底层问题。

P0 · 课程运行时

产品视角

  • 用户进入一天学习时，看到的不是大段教材，而是一组有节奏的学习环节：先想、看懂、自己讲、练习、纠错、总结。
  • 已完成环节可以随时回看，用户不会因为点了“继续”就失去前面内容。
  • 每个环节都能被单独评价和重生成，例如“这个例子太浅”“练习换成工作场景”。
  • 学习首页和计划页不再靠静态卡片表达进度，而是从真实 element 状态推导：未开始、进行中、已完成、需复习。

技术视角

  • 新增 `lesson_flows` / `lesson_elements` / `lesson_attempts` 数据结构，旧 lesson JSON 通过 adapter 兼容读取。
  • 服务端生成统一 `LessonFlow`，前端只负责按 element type 渲染，不再临时解析大段文本。
  • 引入元素状态机：draft → ready → active → answered → reviewed → done / needs_revision。
  • 支持局部重生成：只重写一个 element 或一组 elements，不破坏整天学习记录。

前端呈现

  • 顶部显示当天目标和 6-8 个学习环节，不再让用户迷路。
  • 主体区域一次只聚焦一个环节，侧边保留“本节要点 / 自查清单 / 来源”。
  • 完成后可以回到任意环节查看，不强制线性单向。
  • 已完成内容在资料页沉淀为“我的产出 / 错题 / 要点卡”。

验收标准

  • 任意一天学习都能看到 6-8 个结构化环节。
  • 完成第 3 环节后，仍可点击第 1/2 环节回看。
  • 用户可对单个环节提出要求并重生成，不影响其他环节。
  • 学习记录按 element 保存，学情页能统计每类环节表现。
LessonFlow {
  id, instance_id, week_no, day_no, title, objective,
  elements: [
    { id, type: "source|think|explain|example|practice|produce|check|reflect",
      title, prompt, content, expected_output, status,
      sources: [], attempts: [], feedback: [], quality_score }
  ],
  current_element_id, completion, generated_from, version
}
产品判断：这是下一轮最优先的底座。没有 LessonFlow，学习页视觉再优化也只是“更漂亮地展示一段浅内容”。
2

深度搜索 source_pack：让系统先理解世界，再生成学习内容

解决“harness 这种概念反复误解”“内容没有参考资料”“生成大纲不够前沿和真实”的问题。

P0 · 搜索与资料层

产品视角

  • 用户提出陌生或多义概念时，系统不急着问模板问题，而是先搜索候选含义，再用最可能的解释来确认。
  • 每个学习路径生成前，都有一份“资料依据”：官方文档、权威文章、论文、视频、案例、项目。
  • 每一节课能展示“本节依据”，用户知道内容从哪里来，也能点出去深挖。
  • 如果资料不足，系统要明确标注“资料不足 / 需要补充”，而不是假装知道。

技术视角

  • 把当前搜索能力升级成 `ResearchWorkflow`：query planning → web search → source ranking → extraction → dedupe → summary。
  • 为每个 source 打标签：official / paper / docs / video / case / blog / community，并计算可信度。
  • 对多义词做 semantic candidates，例如 harness 可候选为 DevOps 平台、AI eval harness、agent/tool harness。
  • 将 `source_pack` 绑定到 instance、week、day、element，供生成、展示和后台分析复用。

交互设计

  • 对话首轮可展示“我查到更可能是 X / Y / Z，你是指哪一种？”
  • 学习页展示 2-5 条最关键来源，不把资料堆满页面。
  • 计划页展示每周参考资料类型，让用户感知计划不是凭空生成。
  • 后台展示搜索命中、来源质量、失败原因和用户纠正记录。

验收标准

  • 对 harness、OpenClaw、MCP、FSRS 等概念能先搜索再澄清。
  • 新生成路径至少沉淀 8-20 条可追踪来源。
  • 每个正式学习日内容至少关联 3 条来源或明确说明资料不足。
  • 来源能在学习页、资料页、后台三个地方被查看。
SourcePack {
  id, instance_id, topic, query_plan,
  sources: [
    { title, url, source_type, authority_score, freshness_score,
      relevance_score, excerpt, claims, used_by_elements }
  ],
  ambiguity: { term, candidates, selected_meaning, confidence },
  created_at, provider, trace_id
}
产品判断：source_pack 不只是“加几个链接”，而是 LearnBuddy 内容可信度、概念理解和后续学情分析的共同地基。
3

内容 Critic 质量闸门：把“生成了”变成“生成得足够好”

解决“模型给了内容但太浅”“练习不贴合目标”“讲解没有教学设计”“生成结果无法稳定验收”的问题。

P0 · 质量保障

产品视角

  • 用户不应该看到第一版粗糙内容，系统内部要先自检、打分、修复。
  • 重生成不只是“重新抽一次”，而是能理解用户要求：更实战、更基础、更多例子、换行业场景。
  • 后台能看到低质量内容集中在哪些领域、哪些模型、哪些 prompt 版本。
  • 学习后的反馈会反哺生成：用户觉得“太浅/太难/不准”要变成下一次生成的约束。

技术视角

  • 新增 `ContentCritic`：对每个 LessonFlow 和 element 做多维评分。
  • 评分维度建议包括：准确性、深度、来源完整度、互动性、可执行性、个性化、节奏感。
  • 低于阈值自动 repair：补例子、补来源、加练习、降难度、重写解释。
  • 记录 prompt_version、model、source_pack_id、critic_score、repair_count，方便后续 AB 和追踪。

教学指标

  • 每节必须有“学完能做什么”的可观察产出。
  • 每个重要知识点必须有一个解释、一个真实例子、一个练习、一个自查问题。
  • 对技能型主题要有任务链，对知识型主题要有概念链，对考试型主题要有题型链。
  • 不允许只有概念讲解，没有用户行动。

验收标准

  • 生成内容有质量分和失败原因，不再只有成功/失败。
  • 低于阈值的 element 自动修复，最多尝试 2 次。
  • 用户反馈“太浅/不准/不适合”后，下一版能体现该约束。
  • 后台可以按路径查看内容质量趋势和问题类型。
CriticResult {
  target_type: "lesson_flow|element",
  target_id, scores: {
    accuracy, depth, source_coverage, interactivity,
    personalization, actionability, rhythm
  },
  issues: [{ type, severity, evidence, repair_instruction }],
  pass, repair_count, prompt_version, model, trace_id
}
产品判断：Critic 是 LearnBuddy 从 demo 走向可持续内容质量的关键。它不是“多调一次模型”，而是内容生产线里的质检与返工机制。
