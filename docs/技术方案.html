LearnBuddy 学习伙伴 · 技术方案

这页用于系统化解释 LearnBuddy 的技术结构、关键链路、支付权益底座和 OpenClaw 接入边界。你应该可以通过这页判断当前架构是否合理、哪些模块是主系统真相源、哪些能力只是上层运行时。

技术分层总览

先把层分清楚，再决定问题该放哪一层解决，避免“什么都上 agent”。
层概念作用当前对应
L0确定性能力不依赖 LLM 的判断、调度、掌握度、通知与阶段闸门`scheduler.py` `mastery.py` `phases.py` `notify.py`
L1Tool / Skill把单个能力包装成可复用、可外露的接口`core/tools.py`、统一工具注册表、skill 包
L2Workflow固定编排的产品闭环，比如生成、讲解、自检、推送路径生成、lesson workflow、RAG 讲解、通知编排
L3Dynamic Workflow根据状态和规则动态选路`recommend.py` `replan.py`
L4Agent带长期身份和主动推进能力的角色LearnBuddy 教练、未来个人助理模式
L5外部 Runtime承载高阶自治代理与跨端主动执行OpenClaw / 未来托管 runtime

系统总图

整套系统要按“用户触点层 → 接入编排层 → 核心学习引擎 → 数据真相源 / LLM / 扩展接入”来理解。
关键判断：LearnBuddy 主系统负责学习数据和业务规则，OpenClaw 只做高阶运行时，不接管学习真相源。

关键状态机

订单、订阅、积分、订阅续费、退款等状态机要画清楚，避免“先实现，后填坑”。
状态机状态合法转移
Orderpending / paid / failed / refunded / partial_refunded / closedpending → paid / failed / closed；paid → refunded / partial_refunded；refund 必须同步扣减权益
Subscriptionactive / past_due / canceled / expiredactive → past_due（续费失败）→ canceled 或 active；expired 后权益只读
PointsAccount正常 / 冻结正常 → 冻结（风控）→ 正常；冻结期间不允许消费
PhoneVerification待验证 / 已通过 / 已过期 / 已锁定待验证 → 已通过 / 已过期；连续失败进入已锁定
Masterynew / learning / reviewing / mastered / forgottennew → learning → reviewing → mastered；mastered 可回退至 forgotten

错误处理与回退

生成 / 检索 / 支付 / 推送是高风险环节，必须有可见的 fallback，而不是静默失败。
环节典型失败用户可见回退
LLM 生成上游超时、解析失败、内容审核拒绝显示“生成暂不可用”，保留用户输入，允许重试或切换精简模式
基线评估出题失败 / 判分失败跳过评估直接用对话澄清生成路径，标注“未评估，路径精度下降”
支付下单失败 / 回调超时 / 验签失败订单进入 pending 或 failed；用户重试时复用幂等号；不重复扣款
权益发放数据库失败 / 重复回调幂等键保证一次发放；失败时记录补偿任务，UI 提示“稍后到账”
推送订阅失效 / 渠道不可用退避重试 + 死亡队列；UI 内通知作为兜底
RAG 检索索引为空 / 检索失败直接使用 LLM 通用回答并打标“无资料引用”

安全模型

账号、支付、Agent 接入都需要明确安全边界，不能上线后再补。
场景当前要求
账号密码bcrypt/argon2 hash；不存明文；登录限频；登录失败递增冷却
手机验证码短信 hash + 过期 5 分钟；同一手机 1 分钟内只发 1 条；1 天内最多 5 条
支付回调渠道签名校验；幂等订单号；金额二次比对；异常订单报警
积分账本所有变更必须留 ledger；不允许绕过 ledger 直接改余额
订阅续费扣费前必须确认；失败有通知；自动续费可一键关停
Agent / OpenClaw只能走 tool/skill/MCP 受控接口；不允许直连 DB；危险操作需二次确认
密钥管理仅走环境变量；.env 不进仓库；CI 注入；定期轮换

维度必须采集的信号

异常5xx 比例、上游 LLM 失败比例、未捕获异常、关键任务堆积

部署与性能预算

为了让方案“可执行”，要写明最小部署单元和性能预算。
项当前基线
进程模型FastAPI 单进程 + APScheduler；SSE 长连接用异步任务
数据库SQLite（主），文件 JSON（实例产物）；后续按需迁移 Postgres
缓存进程内 LRU + 命中统计；不强制 Redis
生成接口 P95≤ 8s（不含网络）；超过走精简模式
推荐接口 P95≤ 500ms
支付回调 P95≤ 1.5s；失败重试 3 次
前端首屏≤ 2.5s（4G）；样式不依赖外部 CDN
浏览器兼容最近两个大版本；移动端响应式 360px 起

备份与恢复

账号、订单、积分、学习档案都不能丢。备份要按层做，恢复要演练过。
层级备份策略恢复目标
SQLite 主库每日全量 + 关键表每小时增量 WAL；保留 30 天RPO ≤ 1h，RTO ≤ 30min
学习路径产物每日 rsync 到备份盘；保留 90 天RPO ≤ 24h，RTO ≤ 1h
向量与缓存不备份，丢失可重建—
密钥与配置密钥不入仓库；配置走环境变量与 .env 备份（加密）RTO 取决于环境重建时间

账号、支付与权益技术架构图

账号、支付、积分、订阅和升级模式必须挂在主系统底座上，不能分散到不同触点自行建账。
模块作用
User统一用户主账户，兼容密码与手机号登录
PhoneVerification验证码 hash、有效期、限频和风控审计
Order / PaymentRecord订单状态机、支付回调、验签与幂等
Entitlement订阅和积分等权益统一发放
PointsAccount / Ledger可解释账本，支持付费积分与赠送积分分离

支付链路时序

这条链路必须幂等，否则会出现重复发放或回调丢失问题。
技术边界要固定：支付和账本都属于 LearnBuddy 基础设施，Agent 或 IM 入口只能消费权益，不能绕过主系统直接改账。

OpenClaw 接入边界

这里最容易误解，所以必须单独讲清楚。
问题当前结论
OpenClaw 是什么是个人助理升级模式的运行时和承载层，不是 LearnBuddy 的替身。
谁是学习真相源始终是 LearnBuddy 主系统，包含计划、学情、记忆、推荐和权益数据。
OpenClaw 通过什么接入通过 tools、skill、MCP 和受控 API 接入，而不是直连数据库乱改状态。
OpenClaw 能做什么主动提醒、主动复盘、跨端协助、承接更自由的代理行为。
OpenClaw 不能做什么不能独立维护订单、积分、学习档案和账本。

怎么看当前架构是否 OK

如果你要用这页评估未来几周做得对不对，重点看下面 4 个判断。
第一条

主系统真相源有没有继续统一，而不是让新功能各自建一套状态。

第二条

新能力有没有落在正确层级，是规则层、工作流层还是 Agent 层。

第三条

关键链路有没有回退和幂等，尤其是 LLM、支付、通知这些高风险环节。

第四条

OpenClaw 和 IM 是否只承担上层承载，而没有侵入账本和学习真相源。

工程约束与非目标

这部分是防止架构继续发散的保护线。
学习真相源统一

计划、学情、记忆、推荐、权益都必须归主系统统一维护。

工作流先于 Agent

优先把可验证闭环做稳，再决定哪些场景值得 Agent 化。

LLM 必须有回退

生成失败、检索失败、上游超时都需要用户可见的 fallback。

支付与风控不后补

验证码限频、回调验签、幂等账本、退款补偿都要在设计时就锁死。
