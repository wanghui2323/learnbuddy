本节要解决什么问题

你设计智能客服时，需要决定每条信息该放哪层记忆、用什么策略存取。学完本节，你能根据“访问频率、更新方式、失效条件”三个判断维度，把任何一条信息正确归类到短时/工作/长期记忆，并说出对应的工程实现策略。

先想：一条客服消息该放哪？

用户对客服说：“我要改收货地址，新地址是北京市朝阳区xxx。”这条消息应该存入哪种记忆？

1A. 短时记忆，因为它是当前对话的一部分，对话结束后就不需要了
2B. 工作记忆，因为它是用户正在进行的操作（改地址），需要跨轮维护状态
3C. 长期记忆，因为地址是用户个人信息，需要持久保存
4D. 同时存入短时和工作记忆，因为既需要对话上下文又需要维护操作状态

正确是 D。这条消息有两个角色：作为对话历史的一部分，它需要短时记忆（对话结束即丢弃）；作为地址修改操作的内容，它需要工作记忆来维护跨轮的状态（比如用户可能还要确认新地址）。只选 A 会丢失操作状态，只选 B 会丢失对话上下文，只选 C 则地址会被永久保存但无法在对话中快速引用。

04
compare

三种记忆的工程策略对比

不要问“该用 Redis 还是 PostgreSQL”，要问“这条信息的访问频率、更新方式、失效条件是什么”。

  • title短时记忆：上下文内临时，频繁写入，快速丢弃
    note为什么：对话轮次结束或超时后信息不再需要。判断标准：写入后只在当前上下文内使用，上下文结束即可删除。工程实现：Redis String + TTL（如 30 分钟），或内存 Map + 轮次结束清空。
  • title工作记忆：跨轮次，状态结构，增量更新，手动清理
    note为什么：用户操作可能跨越多个对话轮次（如填表单），需要维护中间状态。判断标准：信息需要在多个轮次间保持，但操作完成后可以删除。工程实现：Redis Hash（字段级更新）+ 无全局 TTL，操作完成时手动删除 Key。
  • title长期记忆：持久化，低频写入，精确检索
    note为什么：用户画像、历史订单等需要长期保存，且查询时要求精确匹配。判断标准：信息写入后很少修改，且需要按 ID 或索引快速查找。工程实现：关系数据库（PostgreSQL/MySQL）或向量数据库（用于语义检索），写入频率低，查询用索引。
mechanism · 为什么同一个 Redis 可以同时做短时和工作记忆？

Redis 提供了多种数据结构（String、Hash、List、Set 等）和过期策略（Key 级 TTL、手动删除）。短时记忆用 String + TTL，天然支持“写入后自动过期”；工作记忆用 Hash，可以只更新某个字段而不影响其他字段，且不设 TTL 防止误删。两者使用不同的 Key 前缀（如 `short:session123` 和 `work:order456`），代码逻辑完全分离。如果混用同一结构（如都用 String + TTL），工作记忆的中间状态会在 TTL 到期时被误删，导致用户操作中断。

boundary · 什么时候不用这种分类？

当系统规模极小（如单轮对话机器人）时，可以全部用内存变量，不需要分层。但一旦涉及多轮、状态维护、持久化，就必须分层。另一个边界：如果长期记忆的写入频率很高（如每轮都写用户行为日志），则应该用时序数据库或消息队列，而不是关系数据库，因为关系数据库的写入瓶颈会拖垮系统。

example

Worked Example：智能客服“改地址”流程

用户发起改地址请求，系统需要决定每条信息的记忆归属。

  • step1
    text用户说：“我要改地址。”
    note这条消息存入短时记忆（对话历史），同时触发工作记忆：创建一个“改地址”状态（Hash Key: work:user123:address_change），初始字段 {step: 'init'}。
  • step2
    text系统问：“新地址是？”用户答：“北京市朝阳区xxx。”
    note新地址文本存入短时记忆（对话历史）；同时更新工作记忆 Hash：HSET work:user123:address_change new_address '北京市朝阳区xxx' step 'address_provided'。
  • step3
    text系统问：“请确认新地址。”用户答：“确认。”
    note确认动作存入短时记忆；工作记忆更新 step 为 'confirmed'。此时系统读取工作记忆中的 new_address，写入长期记忆（UPDATE user_addresses SET address = '北京市朝阳区xxx' WHERE user_id = 123）。
  • step4
    text操作完成，系统手动删除工作记忆 Key：DEL work:user123:address_change。短时记忆在对话结束 30 分钟后自动过期。
    note工作记忆必须手动清理，否则残留状态会干扰下一次改地址操作。短时记忆自动过期，无需干预。
worked_example · 完整推演：如果判断错误会怎样？
  • step1
    text错误判断：把用户提供的地址直接存入长期记忆（不经过工作记忆）。
    note后果：用户可能在确认前反悔，但地址已经写入了数据库，需要额外的撤销逻辑。
  • step2
    text错误判断：把工作记忆也设 TTL（如 30 分钟）。
    note后果：用户填地址耗时超过 30 分钟，工作记忆 Key 自动过期，系统丢失中间状态，用户需要重新开始。
  • step3
    text错误判断：把短时记忆和工作记忆合并到同一个 Redis Key 里。
    note后果：当短时记忆需要清理（如对话轮次切换）时，无法单独删除短时部分，只能整个 Key 删除，导致工作记忆丢失。
  • step4
    text正确做法：短时用 String+TTL，工作用 Hash+手动清理，长期用数据库。
    note三个策略互不干扰，各自按自己的规则运行。
06
example

第二个例子：智能客服“查询订单”

用户查询历史订单，系统需要决定信息的记忆归属。

  • step1
    text用户说：“查一下我上个月的订单。”
    note短时记忆记录对话历史；工作记忆创建查询状态 {step: 'query_init', query_type: 'order'}。
  • step2
    text系统从长期记忆（数据库）中检索该用户上个月的订单列表。
    note长期记忆写入频率低（订单生成时写入），查询用索引（user_id + month）。
  • step3
    text系统返回结果：“您上个月有 3 笔订单，分别是...”
    note结果可以暂存到工作记忆（如 Redis Hash），以便用户后续追问具体某笔订单时快速读取，避免重复查询数据库。
  • step4
    text用户说：“第一笔的物流信息。”系统从工作记忆读取第一笔订单 ID，再查长期记忆获取物流详情。
    note工作记忆在此处起到了缓存作用，减少了数据库查询次数。对话结束后，工作记忆 Key 被手动删除。
mechanism · 为什么工作记忆可以当缓存用？

工作记忆的本质是“跨轮次维护状态”，而查询结果也是一种状态（用户可能继续追问）。把查询结果暂存在工作记忆里，可以避免重复查询数据库。但要注意：如果查询结果很大（如 1000 条订单），应该只存摘要或分页信息，否则会占用过多内存。判断标准：工作记忆存储的数据量应控制在 KB 级，超过 MB 级应考虑用专门的缓存层（如 Redis 单独实例）或直接让用户重新查询。

boundary · 工作记忆和缓存有什么区别？

工作记忆是业务状态的一部分，删除后会影响业务流程（如改地址到一半，工作记忆丢失会导致用户必须重来）。缓存是性能优化手段，删除后只是变慢，不影响正确性。所以：工作记忆必须手动管理生命周期，缓存可以自动过期。不要把业务状态当成缓存来设 TTL，否则会丢失用户进度。

    note短时记忆。验证码有效期通常 5 分钟，过期即丢弃。用 Redis String + TTL 5 分钟。

练习

练习 1

以下哪条信息最适合归入工作记忆？

1A. 用户当前对话的最近一条消息
2B. 用户正在填写的退货申请表单（已填了商品编号，下一轮要填原因）
3C. 用户的会员等级（普通/银卡/金卡）
4D. 用户的历史订单总数

答案：1 · B 正确，因为它需要跨轮次维护状态（表单填写未完成），且需要增量更新。A 是短时记忆（对话结束即丢弃）。C 和 D 是长期记忆（写入频率低，需要持久保存）。

练习 2

如果工作记忆错误地设置了 TTL（如 30 分钟），最可能发生什么？

1A. 工作记忆自动过期，用户需要重新开始操作
2B. 工作记忆和短时记忆同时过期，但短时记忆可以恢复
3C. 长期记忆被误删
4D. 系统性能提升，因为内存占用减少

答案：0 · A 正确。工作记忆存储的是用户正在进行的操作状态，TTL 过期会导致状态丢失，用户必须重新开始。B 错误，短时记忆过期是正常的，但工作记忆不应该自动过期。C 错误，长期记忆不受影响。D 错误，性能提升不能以丢失业务状态为代价。

练习 3

以下哪段代码正确实现了工作记忆的增量更新？

1A. r.set('work:order', json.dumps({'step': 'init', 'item': 'book'}))
2B. r.hset('work:order', mapping={'step': 'init'}); r.hset('work:order', 'item', 'book')
3C. r.setex('work:order', 3600, json.dumps({'step': 'init'}))
4D. r.lpush('work:order', 'step:init')

答案：1 · B 正确，使用 Hash 可以单独更新某个字段而不影响其他字段，实现增量更新。A 使用 String + JSON，更新时需要读取整个 JSON、修改、再写回，效率低且容易丢失并发更新。C 错误地设置了 TTL，工作记忆不应自动过期。D 使用 List，不适合存储结构化状态。
