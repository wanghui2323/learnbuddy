# AI Builder 第一周：把 LearnBuddy 的构建过程一起开源

9 月 1 日开始「100 天 AI Builder」时，我给第一周定的目标，是用一个真实项目，把产品、设计、前后端、Agent 和验证串起来。

这周，我选择把持续迭代的 LearnBuddy 开源。但整理仓库时，一个问题变得很具体：**如果别人只能运行代码，却不知道功能为什么这样设计，这份开源就只交出了一半。**

所以这次除了源码，我也把产品架构、需求文档、AI Design 规范、系统与 Agent 架构、开发工作台整理成了可以对照阅读的产物。它们不是六份独立作业，而是回答同一个问题：

**怎样把一个学习需求，变成别人能理解、能使用，也能继续修改的 AI 产品？**

如果你会用 AI 写页面，却常常卡在“下一步该做什么”，可以把这篇当成一份实战导读。读完带走三样东西：一条能验收的需求写法、一份可以交给 AI 的设计约束，以及一张判断交付是否成立的检查思路。暂时不懂后端也没关系，先跟着用户任务读图，再按需要打开源码。

先说明范围：LearnBuddy 已有此前数月的积累，不是一周从零写成。本周主要围绕开源定位、Cloud / Personal 发行边界、个人 Agent 接入底座和可复用交付材料推进；未通过的验收，也会一起公开。

## 一、先画产品架构：我们到底在构建什么？

假设一个人说：“我想在三个月内准备日语 N3，每天可以学半小时。”

聊天模型能很快给出十二周计划。但真正使用时，问题才开始：他的基础是否够用？今天没完成怎么办？做对一道题，是独立掌握，还是借助 AI 才能完成？学习记录怎样影响下周安排？

这些问题决定了 LearnBuddy 不能只保存一份生成文本。它要管理一条持续变化的学习路径。

![AIGC 产品架构：实体、服务、前端与体验；底部虚线表示代码复用，不表示不同部署间的数据同步](./assets/learning-map/product-architecture-aigc.png)

画这张图时，我先从底部的“实体”开始。实体不是技术名词清单，而是产品需要持续记住的东西：目标、评估、评分证据、能力画像、路径、任务和学习记录。

例如，为什么要把“回答”和“评分证据”分开？因为用户可以保存了回答，却尚未完成判分；模型也可能判错，需要复核。如果把它们压成一个“能力分数”，后面就很难解释这个结论从哪里来。

对象明确后，服务才有了职责：评估服务把作答转成有依据的画像，生成服务消费目标与画像，复习与重规划再消费学习反馈。这样“个性化”不只发生在首次生成，也发生在后续调整。

前端承接这些能力，形成对话、学习空间、路径、学练和自检等入口。用户不需要理解底层模块，却应清楚知道：今天做什么，为什么做，做完后发生什么变化。

**产品架构的价值，是让新增功能有归属。** 比如“飞书提醒”不是又造一个独立学习系统，而是为已有任务和提醒规则增加触达渠道；“学习完成”和“能力掌握”也不能因为界面方便，就合并成同一个百分比。

本周另一个重要判断，是把“低门槛体验”和“长期拥有”分开。

Cloud 由平台提供有限模型额度，支持必要的注册、隔离、用量和管理；Personal 则由个人部署，自备模型 Key、保有数据，可选接入自己的 OpenClaw 和飞书。两者共享代码与能力模型，不是共享各自的私人数据。

这让公有云的责任保持清楚：让人看懂并体验产品，而不是替每个人长期托管一套私人 Agent。

可对照产物：[产品架构与学习地图](https://github.com/wanghui2323/learnbuddy/blob/main/docs/学习地图.html) · [Cloud / Personal 方案](https://github.com/wanghui2323/learnbuddy/blob/main/docs/07-开源与公有云双版本架构.md)。

## 二、再写 PRD：让 AI 知道什么才算做对

架构回答“有什么”，需求文档还要回答“怎样才算完成”。

“支持能力评估”就是一句过宽的要求。AI 可能做出一页题目、一个分数和一个漂亮的雷达图，却没有保存原始回答，也没有处理刷新、判分失败或用户异议。

我在当前 PRD 中，把它写成一条可追踪的需求：**用户提交摸底答案后，能查看带依据的能力诊断；刷新后继续原评估；后续路径使用这次有效诊断。**

写这一条时，需要补齐四组内容。

第一组是用户与范围。谁要完成什么，当前阻碍在哪里，这次做到哪一步。LearnBuddy 必须保留即时基线评估，并区分独立完成与 AI 协作；但不因此顺手扩展出在线监考、大题库或一整套新课程。

第二组是对象与规则。一次评估有自己的 ID，题目、回答和评分证据关联它；没有完成的评估，不能被包装成可信能力结论。独立能力、AI 协作表现和自信，也不能互相替代。

第三组是状态与反馈。提交中怎么防重复？判分中能否离开？失败后保留什么？重进页面时从哪里继续？这些不是开发后的补丁，而是需求的一部分。

第四组是可重复的验收。例如：

- 本人保存第二题后刷新，仍能读回同一次评估和已保存回答。
- 另一个账号请求这次评估，不能读取或修改。
- 判分失败时，页面提示未完成，不能显示“能力为零”或“已掌握”。
- 路径使用有效画像时，补强决策能够追溯到评分依据。

这样写，需求才会同时约束前端、后端和模型调用，而不只是约束页面长相。

当前 [PRD](https://github.com/wanghui2323/learnbuddy/blob/main/docs/01-需求方案.md) 的前半部分按“问题—角色—对象—旅程—规则—验收—追踪”组织，后半部分保留历史需求。重大取舍放进 [SPEC 的 ADR 决策记录](https://github.com/wanghui2323/learnbuddy/blob/main/SPEC.md)，避免把过去某次聊天里的判断误当成最新要求。

你复用时不必照抄整套文档。先选一个真实任务，写清它改变什么、什么不能变、在哪里观察结果，再让 AI 拆开发计划。

## 三、AI Design：先约束体验，再让 AI 画页面

有了 PRD，直接让 AI “做得高级一点”仍然不够。

连续迭代几轮后，很容易出现这样的页面：每页都像能用，但按钮尺寸不一致，主行动不突出，生成状态含糊，失败时只有一条转瞬即逝的提示。问题不一定是审美不好，而是缺少共同约束。

这次补齐的 AI Design 规范，分成两类：**视觉规范决定怎样呈现，交互规范决定怎样回应用户。**

![AI Design 样例：页面合同、视觉变量、组件状态和失败恢复共同约束生成；不是业务页面截图](./assets/learning-map/ai-design-contract.png)

视觉部分规定品牌调性、字体层级、颜色语义、间距、圆角和布局密度。Design Tokens 则给这些决定稳定的名字，让不同页面可以复用，而不是每次重新挑一套颜色。

但同一个绿色按钮，写“继续学习”还是“生成完成”，背后的语义并不相同。交互规范必须继续追问：这个动作改变哪个对象？请求处理中怎么办？何时才允许宣布成功？

以诊断为例，流式文字结束，不代表结果已经保存。页面应区分“正在生成”和“保存成功”；判分失败，也不意味着用户不会。规范要求保留已保存回答、说明未完成的原因，并提供重试入口。

对长任务同样如此。后端只知道当前阶段时，界面就显示阶段，不能为了看起来有进度编出“完成 87%”。AI 给出的推断、学习记录中的事实，以及仍待验证的结论，也要用不同的措辞呈现。

我希望以后每次把页面任务交给 AI，都附上一个很短的约束：

> 先读当前 PRD 和 AI Design。说明这页服务谁、主行动是什么、读写什么对象；补齐默认、加载、成功、失败与恢复状态。复用现有组件和变量，再给出桌面与手机端的验证证据。

这份 [AI Design 执行规范](https://github.com/wanghui2323/learnbuddy/blob/main/docs/AI_DESIGN.md) 已连同可直接复用的 AI 任务模板公开，[视觉规范页面](https://github.com/wanghui2323/learnbuddy/blob/main/docs/设计规范.html) 则保留设计背景与入口。

这里也有一个真实差距：现有页面仍有局部样式和重复变量。本轮交付了规范与样例，不等于全站设计系统已经统一完成。规范的作用，是让下一次改动有依据，也让未达标之处能被检查。

## 四、进到系统内部，看需求怎样变成体验

下面两张是本次实际登录后截取的系统界面。先看它们怎样承接任务，再判断哪些地方值得继续改进。

![真实学习空间：已有 MCP 学习路径、学习状态和继续入口；当前界面截图，不代表新版全部能力已上线](./assets/learning-map/real-learning-space.png)

学习空间承担的是“找回自己的学习任务”。这张截图中，路径名称、当前阶段、已完成数量和继续入口组合在一起，帮助用户回到原来的任务。

同时，它也暴露了可继续优化的地方：目前只有一条路径时，页面留白很多；“还没有学习记录”和“还没有掌握能力”是否区分得足够清楚，也值得继续检查。展示真实界面的意义，恰恰是让这些问题可见，而不是只挑一张看起来丰满的演示图。

进入路径后，可以看到另一层结构。

![真实计划页：长期目标落到阶段、周目标与每日安排；截图中的日期和状态保留原样](./assets/learning-map/real-learning-plan.png)

这里展示的是一个八周 MCP 学习任务：上层是最终目标和每周投入，中间是阶段与周目标，下层是每日安排和进入学习的动作。

值得观察的不是卡片颜色，而是层级关系：每日任务不应与长期目标脱节；“今天可以学”和“尚未解锁”必须有清楚的状态依据。页面一旦承诺某个解锁规则，后端就应该负责校验，而不是只把按钮画灰。

对 Builder 来说，你可以用这两张图反查自己的 PRD：每个重要对象有没有落到用户能理解的位置？每个主要按钮有没有真实结果？发生异常时，用户是否知道该往哪里走？

原始对话入口、内部截图与源码都放进了 [分类交付目录](https://github.com/wanghui2323/learnbuddy/blob/main/docs/README.md)。截图帮助我们讨论体验；是否保存成功、能否恢复，仍要实际操作验证。

## 五、系统与 Agent 架构：把责任放到正确的位置

到这一步，才适合讨论技术架构。因为我们已经知道系统要保存哪些对象、页面会发出什么动作，也知道什么行为不能由模型随意决定。

LearnBuddy 当前采用原生 HTML/CSS/JS 前端、FastAPI 服务，以及 SQLite 和路径文件存储。学习模型通过 API 按需调用，不需要在这台应用服务器上自行训练或部署大模型。

![AIGC 系统总图：Web 与 Personal Agent 调用学习领域服务；即时对话和提醒调度分别执行](./assets/learning-map/system-architecture-aigc.png)

前端负责表达意图、展示过程和结果；后端负责身份、对象归属、额度、状态规则与持久化；学习核心负责评估、生成、学练、记忆和调整；模型负责需要语言与推理能力的生成或辅助判断。

这些边界会直接影响成本和可靠性。例如 Cloud 额度用尽，前端提示“没有额度”并不够。后端必须在调用模型前拒绝，测试还要确认模型函数根本没有执行。否则页面看起来有限额，实际费用仍在产生。

又例如，用户刷新后丢失评估，不该先归因于“模型不稳定”。应该沿页面保存、API 返回、对象 ID 和数据库记录查找，判断是哪一层没有履行责任。

Agent 是这套系统的扩展入口，而不是另一套独立的学习事实库。

在 Personal 方案里，OpenClaw 承担对话运行时和个人飞书通道；LearnBuddy 通过受限工具提供学习能力。MCP 可以理解为连接 Agent 与这些工具的一种接口方式，但工具存在，并不自动意味着整个用户任务完成了。

![Personal Agent 架构：上下文与读取、受控工具执行、结果反馈及失败边界；目标运行合同，真实渠道仍待验收](./assets/learning-map/agent-architecture.png)

Agent 至少要完成四件事：理解请求，取得相关上下文，调用被允许的工具，再依据工具结果回复。上下文应包括当前目标、必要的学习记录和工具说明，而不是把全部私人历史无差别塞进去。

如果用户提出调整需求，Agent 应先读当前状态；缺少必要信息时先澄清；真正写入时，由代码校验身份和归属。工具失败，就说明没有完成，不能仅凭模型生成了“好的”就宣告成功。

自动提醒则走另一条执行路径：LearnBuddy 的调度器根据规则检查到期任务、生成队列并管理投递重试。OpenClaw 不再同时轮询这份队列，避免出现两个系统各发一遍的情况。

这也是本周没有为公有云用户统一托管 OpenClaw 的原因之一：个人 Agent 的凭据、工具权限和运行环境需要明确的归属。先把 Web 学习闭环和受限工具做稳，再扩展个人渠道，责任更清楚。

可沿 [工具契约](https://github.com/wanghui2323/learnbuddy/blob/main/core/tools.py)、[MCP 入口](https://github.com/wanghui2323/learnbuddy/blob/main/mcp_server.py) 和 [个人部署指南](https://github.com/wanghui2323/learnbuddy/blob/main/docs/PERSONAL_DEPLOYMENT.md) 继续研究。当前本地接入底座已有实现，但真实 OpenClaw 与飞书往返、定时送达仍需独立验收。

## 六、开发工作台：让下一次迭代有明确起点

当需求、规范、代码和验证越来越多，只靠一段聊天总结，就很难知道哪份方案还有效。

LearnBuddy 的开发工作台不是学习者使用的“学习空间”，而是开发过程中持续维护的项目页面。它把版本、需求池、技术方案、任务树和验收入口放在一起。

![完整开发工作台的总览页面：版本范围、任务进度与需求、技术、验收入口；不是临时说明卡](./assets/learning-map/workbench-overview.png)

文章里展示总览，[完整工作台页面](https://github.com/wanghui2323/learnbuddy/blob/main/docs/LearnBuddy项目工作台.html) 和 [全页截图](https://github.com/wanghui2323/learnbuddy/blob/main/docs/assets/learning-map/workbench-full.png) 可继续打开查看。它目前是人工维护的静态 HTML，不是与 GitHub 自动同步的项目管理平台。

工作台最重要的不是“完成了百分之几”，而是依赖和退出条件。

以 V0.53 的可信诊断为例：先保存评估对象与原始回答，才能产生评分证据；证据具备后，结果页才能解释画像；画像可信后，路径生成才能消费它；最后才进入完整验收和发布。

因此任务树里的 V053-03、V053-06、V053-07 和 V053-10 不是随意编号的四项待办。它们分别连接判分、结果呈现、路径消费与发布门。任何一段没通过，后面都不能因为“页面已经有了”就算完成。

对 AI Coding 也一样：任务需要带着当前需求、相关规范、负责模块和完成证据进入上下文；改完之后，要把真实差异、检查结果与未达标项写回。这样下一个人、下一次会话才能接着做。

工作台截图中 398 tests 是当时 V0.53 阶段记录，不是这次新增的测试数量。工程测试、人工评分、真实渠道和线上回归各自证明不同的事，不能用一个绿色数字替代全部验收。

### 跟着做一次：不用付费调用模型，也能验证一条产品规则

先做一个更小的练习：**Cloud 额度为零时，系统应拒绝新的模型任务。** 你不需要先部署飞书，也不需要先读懂全部源码。

**第一步，写预测。** 在运行之前记下：“没有额度时，后端返回 429；创建评估、请求 AI 辅助、提交判分这三个入口都不能调用模型。”这里 429 是接口的拒绝结果，不能只检查页面有没有提示。

**第二步，找证据。** 打开 [运行模式测试](https://github.com/wanghui2323/learnbuddy/blob/main/tests/test_runtime_modes.py)，找到名称包含 `zero_credit_guard` 的用例。它用临时数据库建立零额度账号，把三个模型函数替换成“一旦被调用就立即让测试失败”的检查器。这就把“没有额外模型费用”的产品承诺，变成了可执行反例。

**第三步，运行并对照。** 按仓库 README 安装依赖、激活项目环境后，在仓库根目录执行：

```bash
python -m pytest tests/test_runtime_modes.py \
  -k zero_credit_guard -q
```

这条测试不需要真实模型 Key，也不发送飞书消息。预期结果是选中的一个用例通过；如果失败，先区分是依赖未安装、测试环境异常，还是产品守卫真的不符合预测。不要为了拿到绿色结果，把拒绝断言删掉。

**第四步，写出自己的收获。** 用四行记录结束这次练习：运行入口、本次验证、预测与实际、下一步判断。尤其补一句：“它证明三个模型入口在零额度下被拒绝，但不证明所有入口都安全，也不证明线上配置正确。”

如果你暂时不写代码，就完成前两步，再把同一方法迁移到一个页面：写出失败时保留什么、提示什么、允许怎样继续。下一次交给 AI 的，就不再是“帮我优化一下”，而是一条能被检查的任务。
