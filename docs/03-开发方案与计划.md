## 3. 当前整体需求方案

### 3.1 产品定位

LearnBuddy 的目标不是做课程平台，也不是做一个普通 AI 聊天助手，而是做一个面向任意学习领域的 **个性化学习系统 + 长期学习伙伴**。

当前不变的产品哲学：

| 核心机制 | 当前判断 |
|---|---|
| 对话引擎 | 必做，不可砍 |
| 即时基线评估 | 核心差异点，不可砍 |
| 个性化路径生成 | 核心交付物，不可砍 |
| 反遗忘机制 | 必须逐步工程化 |
| 6 关自检 + R 规则 | 必须从模板走向交互页 |
| 个人记忆系统 | 决定产品能否“越用越懂你” |

### 3.2 用户模式分层

未来产品对用户明确分成两种模式：

| 模式 | 定位 | 面向用户 | 核心能力 | 收费 |
|---|---|---|---|---|
| **标准学习模式** | 默认模式 | 大多数普通用户 | 路径生成、学练、学情、推荐、复习、基础推送 | 免费或基础订阅 |
| **个人助理模式** | 升级模式 | 愿意为更主动陪伴付费的用户 | 托管的专属学习助理、长期记忆、主动提醒、主动复盘、跨端联动、IM 对话入口 | 额外收费，用户自行选择开通 |

### 3.3 个人助理模式的产品定义

个人助理模式不是“再做一个聊天窗口”，而是让用户拥有一个平台托管的专属学习代理。

当前对这条线的定义如下：

| 维度 | 当前定义 |
|---|---|
| 产品角色 | LearnBuddy 的升级模式 / Pro 能力层 |
| 用户体验 | 每个用户拥有一个长期陪伴的专属学习助理 |
| 技术实现 | 一人一个 `agent identity + state`，不承诺一人一个物理独立实例 |
| 跨端能力 | PC 负责深度学习，移动端负责提醒、复盘、小测与轻交互 |
| 移动入口 | 未来可接 Web Push / 飞书 / 微信等触点，对话能力由 agent 层统一承接 |
| 收费方式 | 用户自行选择是否开通，升级后额外付费 |

### 3.4 当前边界

为了避免范围失控，当前明确边界如下：

- 当前主线仍然是 **LearnBuddy Web/PWA 主产品**
- 当前不做“为每个用户起一个独立 OpenClaw 物理实例”
- 当前不做独立移动 App
- 当前不让 IM 入口成为数据真相源，学习数据仍以 LearnBuddy 主系统为准

### 3.5 账户与商业化需求

这部分现在正式进入高优先级需求，不再只是远期想法。

| 能力 | 当前判断 | 备注 |
|---|---|---|
| 手机验证码注册登录 | 高优先级 | 未来要支撑更低门槛注册、移动端触达和正式转化 |
| 支付能力 | 高优先级 | 未来要支撑升级模式开通、套餐购买、权益发放 |
| 积分体系 | 高优先级 | 不直接按 token 对用户计价，改成面向用户的积分账户 |
| 赠送积分 | 必须支持 | 用于拉新、补偿、活动、试用和运营激励 |

当前商业化原则：

- 面向用户的计费单位是 **积分**，不是 token
- token 只作为系统内部成本核算参考，不直接暴露给用户
- 支付买到的是积分或套餐权益，再由积分驱动学习服务消耗
- 个人助理模式未来可以按 **订阅 + 积分** 混合方式设计

### 3.6 账户体系方案

当前推荐的账户策略不是推翻现有账号体系，而是做**兼容式扩展**：

| 能力 | 方案 |
|---|---|
| 现有账号体系 | 保留当前邮箱/密码或现有登录方式，避免强迁移 |
| 手机验证码登录 | 作为新增快速注册/登录方式 |
| 手机号绑定 | 用户可在已有账号上补绑手机号 |
| 账号合并原则 | 一个用户只有一个主账户，手机号、邮箱、第三方方式都绑定到这个账户 |
| 风控要求 | 验证码限频、设备/IP 基础风控、异常登录提醒 |

当前判断：

- 对用户来说，应该是“多种登录方式进入同一个账户”
- 对系统来说，应该是“一个用户对应一个统一的权益、记忆、学习档案和积分账户”

#### 3.6.1 手机验证码登录前置依赖

| 前置项 | 说明 |
|---|---|
| 短信服务商 | 需要稳定短信通道、签名、模板与成本测算 |
| 登录风控 | 需要限频、设备/IP 限制、验证码有效期与异常拦截 |
| 账号绑定策略 | 需要明确“新手机号注册”与“老账户绑定手机号”的流程 |
| 用户协议与隐私 | 需要补手机号采集、用途与安全说明 |
| HTTPS 与回调环境 | 线上环境必须稳定，避免验证码流程在公网出问题 |

### 3.7 支付与积分方案

#### 3.7.1 设计原则

| 原则 | 说明 |
|---|---|
| 用户理解简单 | 面向用户只讲积分和权益，不讲 token |
| 成本可映射 | 积分在内部可映射模型成本与服务成本 |
| 运营可调节 | 支持赠送、补偿、活动、试用，不把价格体系绑死在 token 上 |
| 收费可分层 | 标准模式与个人助理模式可共用一套积分账户体系 |
| 流水可追溯 | 所有充值、赠送、扣减、退款、补偿都有记录 |

#### 3.7.1.1 支付前置依赖

| 前置项 | 说明 |
|---|---|
| 支付通道选择 | 需要先定微信支付、支付宝或聚合支付策略 |
| 商品与套餐配置 | 需要先定义积分包、订阅、升级模式权益是什么 |
| 订单与回调 | 需要幂等订单号、支付回调验签与重复通知处理 |
| 权益发放 | 支付成功后积分或订阅权益发放必须幂等 |
| 退款与补偿 | 需要明确退款时积分回收、已消耗积分如何处理 |
| 财务与风控 | 至少需要基础对账、异常订单、刷单/套利防护 |

#### 3.7.2 积分账户最小闭环

| 模块 | 作用 | 最低要求 |
|---|---|---|
| 积分账户 | 记录用户当前可用积分余额 | 可查余额、可查冻结/待结算状态 |
| 积分流水 | 记录每次增减的来源与用途 | 充值、赠送、扣减、退款、补偿都可追溯 |
| 订单 | 记录用户购买行为 | 可关联支付单、权益发放结果 |
| 支付单 | 记录第三方支付状态 | 待支付 / 成功 / 失败 / 关闭 |
| 权益发放 | 订单支付成功后给用户发积分或订阅权益 | 必须幂等，防重复发放 |
| 退款/补偿 | 支持回滚或补差 | 退款后可扣回未使用积分，补偿可追加赠送积分 |

#### 3.7.3 积分来源

| 来源 | 用途 |
|---|---|
| 充值购买 | 用户主动购买积分包或套餐 |
| 订阅附赠 | 标准订阅或个人助理订阅按周期赠送 |
| 运营赠送 | 拉新、活动、节日、试用 |
| 客服补偿 | 故障补偿、退款补差 |
| 内测奖励 | dogfood、反馈奖励 |

#### 3.7.4 积分消耗方向

| 场景 | 当前建议 |
|---|---|
| 基础学习能力 | 尽量按套餐或低频积分消耗，不让用户觉得处处扣费 |
| 重型生成能力 | 可按积分消耗，例如高强度生成、深度重规划、特殊报告 |
| 个人助理模式 | 更适合“订阅打底 + 额外积分” |
| 运营试用 | 优先用赠送积分承接，而不是直接送现金权益 |

### 3.8 收费结构建议

当前更适合的收费结构不是单一一种，而是分层：

| 层 | 形式 | 说明 |
|---|---|---|
| 标准模式入门 | 免费 / 低价基础订阅 | 先让用户进入系统，降低门槛 |
| 标准模式增强 | 积分包或基础套餐 | 覆盖额外生成、复盘、个性化服务 |
| 个人助理模式 | 升级订阅 | 购买“托管的专属学习助理”能力 |
| 高阶消耗 | 积分补充包 | 承接超额使用、活动包、定向服务 |

当前结论：

- **不要把所有价值都做成纯积分包**
- **也不要把所有能力都锁进高价订阅**
- 最合理的是：`订阅负责身份与持续服务，积分负责弹性消耗与运营调节`

### 3.9 个人助理模式与收费关系

| 维度 | 当前建议 |
|---|---|
| 开通方式 | 用户主动选择升级 |
| 计费方式 | 月/季/年订阅优先 |
| 配套权益 | 可附带固定积分额度 |
| 超额部分 | 再用积分包补充 |
| 用户价值表达 | 卖的是“更主动、更持续的陪伴”，不是卖 token |

### 3.10 当前待定事项

| 问题 | 当前倾向 |
|---|---|
| 先上纯积分包还是先上订阅 | 倾向先做积分账户 + 基础套餐，再叠加订阅 |
| 积分是否过期 | 倾向赠送积分可过期，付费积分不过期或超长有效期 |
| 个人助理模式是否单独赠送积分 | 倾向赠送，形成清晰权益感知 |
| 是否区分“付费积分”和“赠送积分” | 倾向区分，便于退款、补偿与风控 |

## 4. 当前技术方案

### 4.1 总体架构

| 层 | 当前角色 | 说明 |
|---|---|---|
| Web / PWA 层 | 用户主入口 | `index` / `instance` / `space` / 推送订阅 / 学练与学情展示 |
| 服务层 | 编排与 API | `server.py` 负责 SSE、鉴权、实例 API、lesson / analytics / recommend / push / admin |
| Core 引擎层 | 学习内核 | `engine` / `generator` / `content` / `concepts` / `rag` / `memory` / `recommend` / `replan` / `scheduler` |
| 数据层 | 用户与学习真相源 | SQLite 承载用户/行为/反馈/追踪，JSON/Markdown 保留路径档案与学习产物 |
| 扩展层 | 升级模式预埋 | MCP / tools / 未来 agent runtime / OpenClaw skill 包 |

### 4.2 当前技术原则

| 原则 | 当前要求 |
|---|---|
| 确定性优先 | 能不用 LLM 就不用 LLM，推荐/重规划/调度优先走规则 |
| 学习真相源统一 | 计划、学情、记忆、推荐都以 LearnBuddy 主系统为准 |
| LLM 有回退 | 所有模型调用必须有可见 fallback 或错误提示 |
| 工作流先于 Agent | 先把产品闭环做扎实，再把 agent 接到上层 |
| OpenClaw 是升级模式 | 不重做主产品，不替代主系统，只做高阶代理外骨骼 |

### 4.3 当前技术结论

- 核心学习引擎已经成形，不需要推倒重来
- 下一步重点不是补更多“点状功能”，而是收口关键链路
- 个人助理模式的前提是先把主系统 tools / memory / scheduler 稳定下来
